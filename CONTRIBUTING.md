# Contributing to ProveBench

ProveBench is only useful if every row is comparable. Most of this guide is about keeping implementations equivalent and numbers honest.

## Dev setup

Prerequisites:

- Node 20 or newer
- `nargo` 1.0.0-beta.19 (`noirup -v 1.0.0-beta.19`)
- `bb` 4.0.0-nightly.20260120 (`bbup -v 4.0.0-nightly.20260120`)
- Optional: `circom` 2.2.x, only to rebuild Circom circuits or recount constraints

```bash
npm install                  # root: runner, scripts, lint tooling
npm --prefix web install     # browser suite
bash scripts/get-rapidsnark.sh
```

## Checks to run before a PR

```bash
npm run lint                 # ESLint (runner, scripts, web app)
npm run format:check         # Prettier + nargo fmt --check
npm run build:noir           # recompile circuits; commit artifacts/noir if they change
node bench/run.mjs --reps 1 --workloads cap_check,merkle20 --machine smoke   # smoke run, then delete results/smoke.*
npm run web:build            # typecheck + production build of the browser suite
```

`npm run format` fixes formatting. CI runs the same checks (`.github/workflows/ci.yml`). There is no unit test suite: every benchmark cell verifies its own proof, and the runner exits non-zero if any cell fails.

## Project layout

```
circuits/noir/<workload>/        Noir package (Nargo.toml, src/main.nr, Prover.toml)
circuits/circom/<workload>.circom
inputs/<workload>.json           shared inputs, generated by scripts/gen-inputs.mjs
artifacts/                       compiled circuits, keys, circuit-sizes.json
bench/run.mjs                    native runner; bench/*-worker.mjs run in-process timings
scripts/                         input generation, builds, sizes, summary, rapidsnark fetch
results/                         native results; results/browser/ for browser results
web/                             Vite static app (browser suite)
```

## Adding a workload

A workload is a statement, not a circuit. Every implementation must prove the same statement.

1. **Write down the statement** in one sentence, including which values are public and which are private. That sentence goes into the README workload table.
2. **Inputs**: add a block to `scripts/gen-inputs.mjs` that derives the inputs from the seeded PRNG (never `Math.random`) and computes any public outputs with a reference implementation in JS. Run `npm run inputs`. Both `inputs/<id>.json` and `circuits/noir/<id>/Prover.toml` are written from the same object.
3. **Noir**: add `circuits/noir/<id>/`. Run `npm run build:noir`.
4. **Circom** (if feasible): add `circuits/circom/<id>.circom`, add its ptau size to `ptau_for` in `scripts/build-circom.sh`, and run `bash scripts/build-circom.sh <id>`. Use the same public signals in the same order as the Noir `pub` parameters.
5. **Register it** in `WORKLOADS` in `bench/run.mjs`, in `web/src/workloads.ts`, and in the `W` list in `scripts/summarize.mjs`. Run `node scripts/sizes.mjs` to update gate and constraint counts.
6. **Check equivalence**: both implementations must accept the generated inputs and reject a tampered one (flip one private input and confirm proving fails). Say in the PR how you checked.

Equivalence rules:

- Same hash function and parameters across systems. If a system has a cheaper native hash (Poseidon2 in Noir), add it as a separate `variant` row, never as the main comparison.
- Same range checks. If one side constrains values to 64 bits, the other must too.
- No precomputed hints that move work out of the circuit on one side only.
- Do not tune one implementation and leave the other naive. If you optimise, optimise both or document why not.

## Adding a proving system

1. Add a runner function in `bench/run.mjs` next to `runNoir` / `runRapidsnark` / `runSnarkjs`, and add its id to `SYSTEMS`. It must return the same shape: `witness_ms`, `prove_ms`, `verify_ms` (via `stats()`), `proof_bytes`, `peak_rss_mb`, `verified`, `size` and `notes`.
2. Time it the same way as the others: one warmup, then N timed reps. If it is a CLI, call it through `timed()` so wall clock and peak memory are captured consistently. Say in `notes` what the timing includes (process start, key loading, and so on).
3. Verify every proof. A cell whose proof does not verify must report `verified: false` or throw, never succeed silently.
4. Pin the toolchain version and record it in `toolchain()`.
5. For the browser, add the system to `SYSTEMS` in `web/src/workloads.ts` and a runner in `web/src/bench.ts`.
6. Explain in the README what the system's size unit means (gates, constraints, cycles) and why it is not directly comparable with the others.

## Submitting a result

- **Browser**: open the page, run the suite, click "Export result JSON", and open a PR adding the file to `results/browser/`. Fill in `device.model` if your browser did not detect it, and add a `note` field saying what else was running on the device.
- **Native**: run `npm run bench -- --reps 7 --cooldown 15 --note "<what else was running>"`. Commit `results/<machine>.json` and `.md`, then run `node scripts/summarize.mjs`.

Every result must say what else was running. "Idle" is a claim; if a browser, an IDE or a build was open, say so. Results are never edited by hand except to fill in a device model the browser could not detect.

## Style

- Comments explain why, not what.
- No em dashes in docs or UI copy.
- Plain commit messages, one change per commit.
